# 1 自动化文档结构元数据格式规范

> **文档版本**：v2.0  
> **最后更新**：2026-05-15  
> **维护者**：开发团队  
> **适用范围**：GB/T 8567‑2006 规定的软件开发文档中的结构化元数据嵌入  
> **目的**：为从国标文档自动生成代码或进行高精度还原提供精确的机器可读信息。
> **适用团队规模**：2‑5 人

---

## 1.1 引言

### 1.1.1 背景

在传统国标文档中，大量设计信息以自然语言描述，难以被 AI 或自动化工具直接解析，导致从文档到代码的还原精度低、耗时长。本规范定义了在国标文档特定章节嵌入 **YAML 格式的结构化元数据** 的标准，使得文档不仅可读，而且 " 可执行 "——AI 可以直接读取这些元数据生成代码、测试用例、数据库表等。

### 1.1.2 与 MCP 工具链的关系

本规范中的元数据块是 MCP 工具链中 `generate-gb-docs` Skill 的输出格式，也是《基于国标文档的高精度代码还原方案》中正向还原和反向提取工作流的数据基础。通过该规范，国标文档成为设计与代码之间的精确契约。

### 1.1.3 对小团队的价值

- **减少沟通成本**：设计即文档，文档即数据，无需额外维护设计信息。
- **提高自动化程度**：AI 可自动从 YAML 块生成代码骨架、接口定义、测试用例。
- **便于维护**：元数据与自然语言共存于同一文档中，修改时同步更新。
- **降低工具依赖**：即使未实现全套 MCP 工具，团队也可通过简单脚本解析 YAML 块，实现半自动化。

### 1.1.4 文档格式选择

本规范采用 **Markdown + YAML Front Matter + YAML 代码块** 的混合格式。这套格式具备以下优势：

- **原生 AI 友好**：YAML 和 Markdown 是模型训练中的常见数据，AI 天生就能理解，省去大量解释格式的 Token，交互效率更高。
- **渐进式学习曲线**：在熟悉的文档编写体验上增加少量标记，学习成本低，不会造成负担。
- **完全可逆与零依赖**：即使在纯文本环境下也能清晰阅读和手动编辑，不依赖任何特定工具或平台，保证文档的长期可维护性。
- **可与 Git 完美结合**：纯文本格式天然适合版本控制，方便追踪每次设计决策的变更，并通过 CI 流水线进行自动化校验。
- **强大的扩展性**：YAML 格式能轻松支持嵌套结构、列表和键值对，能表达复杂的设计关系。

## 1.2 通用规则

### 1.2.1 文档级元数据

每个国标文档的文件头部必须包含 YAML Front Matter，用于声明文档级元数据和 AI 操作指令。Front Matter 位于文件最顶部，使用 `---` 包裹，与正文之间**空一行**。

**必选字段：**

| 字段 | 类型 | 说明 | 示例值 |
|------|------|------|--------|
| 标准 | 字符串 | 遵循的标准编号 | `GB/T 8567-2006` |
| 版本 | 字符串 | 文档版本号（语义化版本）| `1.0.0` |
| 生成时间 | 日期 | 文档生成日期 | `2026-05-15` |
| 文档名称 | 字符串 | 包含序号和全称 | `11 - 软件需求规格说明 (SRS)` |
| 项目名称 | 字符串 | 所属项目名称 | `任务管理系统` |

**可选字段——AI 操作指令：**

使用 `@` 前缀标识 AI 操作指令，避免与标准 YAML 键名冲突。包含特殊字符的键必须用引号包裹。

| 指令键 | 含义 | 可选值 |
|--------|------|--------|
| `'@ai-rewrite'` | 全量重写时的人类内容处理方式 | `preserve`（保留）、`rewrite`（可覆盖，默认）|
| `'@ai-merge'` | 新增内容的合并策略 | `append`（追加）、`replace`（替换，默认）|
| `'@ai-human-sections'` | 受保护的人类内容章节模式列表 | 字符串数组，支持 `*` 通配符匹配标题 |

**完整示例：**

```yaml
---
标准: GB/T 8567-2006
版本: 1.0.0
生成时间: 2026-05-15
文档名称: 11 - 软件需求规格说明 (SRS)
项目名称: 任务管理系统
'@ai-rewrite': preserve
'@ai-merge': append
'@ai-human-sections':
  - "## 3.*"
  - "## 4.*"
---
```

**指令说明：**  
当执行 `generate-gb-docs --enhanced` 全量重写时，AI 会读取 `@ai-rewrite` 指令，识别 `@ai-human-sections` 指定的章节，将这些章节的自然语言描述**原样保留**，只更新 YAML 块或在章节末尾追加新的结构化内容。新增的章节则完整生成。这确保了人类文字永远是主人，AI 只是帮手。

### 1.2.2 元数据块规则

1. **元数据块位置**：必须嵌入在特定章节的末尾（详见第 1.4 节汇总表），与前一正文之间**空一行**。
2. **格式**：YAML 代码块，使用 ` ```yaml ` 标记，键名统一使用**简体中文**。
3. **编码**：UTF‑8 无 BOM。
4. **可选性**：未标注 " 必选 " 的字段为可选，可为空或省略，不影响整体解析。
5. **多实例**：若一个章节中有多个同类元素（如多个功能需求、多个接口），则应**分别嵌入各自的元数据块**，而非合并为一个块。每个块独立存在。
6. **文档变更**：当文档内容更新时，对应的元数据块**必须同步更新**，确保自然语言描述与结构化数据一致。
7. **人类内容保护**：正向还原时 AI 只读取 YAML 块生成代码，不修改文档；反向提取时 AI 只更新 YAML 块，自然语言描述部分保持不动。

## 1.3 元数据类型定义

### 1.3.1 功能–用于 SRS（软件需求规格说明）第 4.3 节 " 功能需求 " 每个功能项末尾

**类型标识**：`功能`

| 字段 | 类型 | 必选 | 说明 | 示例值 |
|------|------|------|------|--------|
| 名称 | 字符串 | 是 | 功能的唯一标识名称 | `用户登录` |
| 描述 | 字符串 | 是 | 功能简要描述 | `用户通过用户名和密码登录系统` |
| 输入 | 字符串或列表 | 是 | 输入数据描述 | `用户名: string; 密码: string` |
| 输出 | 字符串或列表 | 是 | 输出数据描述 | `登录成功: token; 失败: 错误码` |
| 前置条件 | 字符串或列表 | 否 | 执行前必须满足的条件 | `用户已注册` |
| 后置条件 | 字符串或列表 | 否 | 执行后产生的状态变化 | `系统生成会话令牌` |

**示例**：

```yaml
功能:
  名称: 用户登录
  描述: 验证用户名和密码，返回访问令牌
  输入:
    - 用户名: string
    - 密码: string
  输出:
    - 访问令牌: string
    - 错误消息: string
  前置条件:
    - 用户已注册
    - 系统处于活动状态
  后置条件:
    - 用户会话已建立
```

**类型标识**：`组件`

| 字段 | 类型 | 必选 | 说明 | 示例值 |

| 依赖 | 字符串列表 | 否 | 依赖的其他组件名称 | `数据库模块`, `日志模块` |

### 1.3.3 状态–用于 SDD（软件结构设计说明）第 4.2 节 " 全局数据结构说明 " 末尾

**类型标识**：`状态`

| 字段 | 类型 | 必选 | 说明 | 示例值 |
|------|------|------|------|--------|
| 变量 | 列表 | 是 | 每个变量包含以下子字段 | 见下 |
| 变量.名称 | 字符串 | 是 | 变量名 | `currentUser` |
| 变量.类型 | 字符串 | 是 | 基本类型或自定义类型 | `User` 或 `string` |
| 变量.默认值 | 任何 | 否 | 初始值 | `null` |
| 变量.值列表 | 列表 | 否 | 若为枚举，列出所有可能值 | `['未登录', '普通用户', '管理员']` |
| 变量.描述 | 字符串 | 是 | 变量含义 | `当前登录的用户信息` |

**示例**：

```yaml
状态:
  - 变量:
      名称: 当前用户
      类型: 用户对象
      默认值: null
      描述: 当前登录的用户信息，未登录为空
  - 变量:
      名称: 会话令牌
      类型: 字符串
      默认值: ""
      描述: JWT 令牌
```

### 1.3.4 接口–用于 IDD（接口设计说明）第 3.x 节每个接口描述末尾，或用于 SDD 第 4.5.2 节每个接口末尾

**类型标识**：`接口`

| 字段 | 类型 | 必选 | 说明 | 示例值 |
|------|------|------|------|--------|
| 名称 | 字符串 | 是 | 接口名称 | `parseTaskLine` |
| 方向 | 字符串 | 是 | 取值：`输入` / `输出` / `双向` | `输入` |
| 类型 | 字符串 | 是 | 调用方式：`函数调用` / `消息` / `数据流` | `函数调用` |
| 数据元素 | 列表 | 是 | 每个元素包含 `名称`, `类型`, `范围`, `精度` | 见下 |
| 数据元素.名称 | 字符串 | 是 | 参数或字段名 | `line` |
| 数据元素.类型 | 字符串 | 是 | 数据类型 | `字符串` |
| 数据元素.范围 | 字符串 | 否 | 合法值域 | `1-1024 字符` |
| 数据元素.精度 | 字符串 | 否 | 数值精度 | `0.001` |

**示例**：

```yaml
接口:
  名称: 解析任务行
  方向: 输入
  类型: 函数调用
  数据元素:
    - 名称: 任务行文本
      类型: 字符串
      范围: 1-1024 字符
      精度: 不适用
  协议: 同步调用
  错误码:
    - 格式错误
    - 空内容
```

### 1.3.6 事件流–用于 SDD 第 5.x 节（模块详细设计）每个模块末尾

**类型标识**：`事件流`

| 字段 | 类型 | 必选 | 说明 | 示例值 |
|------|------|------|------|--------|
| 步骤 | 列表 | 是 | 每个步骤包含 `触发`, `动作`, `下一步` | 见下 |
| 步骤.触发 | 字符串 | 是 | 触发事件描述 | `用户点击未完成按钮` |
| 步骤.动作 | 字符串 | 是 | 执行的动作 | `设置 filterMode='active'` |
| 步骤.下一步 | 字符串 | 是 | 触发后续动作或状态 | `刷新视图` |
| 伪代码 | 字符串 | 否 | 事件处理的可执行伪代码，提升还原精度 | 见示例 |

**示例**：

```yaml
事件流:
  步骤:
    - 触发: 用户选择"未完成"
      动作: 设置过滤模式 = 'active'
      下一步: 重新渲染任务列表
    - 触发: 过滤模式改变
      动作: 调用 applyFilter()
      下一步: 更新显示内容
  伪代码: |
    function onFilterChange(newMode: FilterMode): void {
      filterMode = newMode;
      const filtered = applyFilter(taskList, newMode);
      renderTaskList(filtered);
    }
```

### 1.3.7 关键条件–用于 SDD 第 5.x 节（模块详细设计）每个模块末尾

| 边界条件 | 字符串列表 | 否 | 边界情况和异常处理 | `输入空数组时返回空数组` |

**示例**：

```yaml
关键条件:
```

## 1.5 使用指南（2‑5 人团队）

### 1.5.1 如何从 `architector` 导出 YAML 块

1. **前提**：已使用 `develop-architector-mcp` 录入了模块详情（如接口的 inputs/outputs、状态变量等）。
2. **自动生成**：调用 `generate-gb-docs` Skill，Skill 会自动将 `architector` 中的结构化数据填充到国标文档的 YAML 块中。
3. **手动补充**：若 Skill 未就绪，可使用 `architector get-module-details` 获取数据，然后按本规范格式手动填入文档。

### 1.5.2 如何手动编写和校验 YAML 块

**编写建议**：

- 使用支持 YAML 语法高亮的编辑器（VS Code 默认支持，推荐安装 `YAML` 插件进行实时校验）。
- 缩进使用 **2 个空格**，禁止使用 Tab。
- 字符串一般不需要引号，但包含冒号或特殊字符时使用双引号。如：`描述: "状态: 成功"`。
- 多行字符串使用 `|` 保留换行，或使用 `>` 折叠为空格。推荐使用 `|` 以保持可读性。
- 每个 YAML 块前可加 `---`（可选，但推荐），以便于解析器识别块边界。

**校验方法**：

- 在线 YAML 校验器（如 yamllint.com）。
- VS Code 插件 `YAML` 实时校验。
- CI 中集成 `yamllint` 命令对 `docs/gb/*.md` 中的 YAML 块进行检查，确保格式正确。

### 1.5.3 如何利用 `generate-gb-docs` Skill 自动生成

1. **前提**：已创建 `task-master` Spec，并完成了设计阶段。
2. **执行**：在 Cline 中输入：
   `用 generate-gb-docs 技能执行生成所有国标文档，基于 Spec ID: spec-xxx`。
3. **产出**：`docs/gb/` 目录下各文档将自动包含正确的 YAML 块。
4. **若 Skill 不可用**：可手动调用 MCP 工具链（`task_spec export`、`architector list_all_modules`、`narsil-mcp get_call_graph` 等），由 AI 辅助填充模板。

### 1.5.4 如何将 YAML 块转换为代码骨架（正向还原）

参见《基于国标文档的高精度代码还原方案》的正向还原工作流。主要步骤为：

1. **读取国标文档**：通过 `rust-filesystem-mcp read_file` 或直接在 Cline 中读取。
2. **生成代码**：AI 自动解析 YAML 块并生成对应代码骨架。
3. **写入文件**：通过 `rust-filesystem-mcp write_file` 保存。

### 1.5.5 版本管理与团队协作

- **版本控制**：所有国标文档（包括 YAML 块）必须纳入 Git 管理，便于追踪每次设计变更。
- **PR 检查**：在 PR 模板中增加 Checklist 项：" 设计变更是否同步更新了国标文档中的 YAML 块？"
- **角色分工**（2‑5 人）：
	- **设计师/架构师**（1‑2 人）：负责填写 SSDD、IDD、SDD 中的元数据。
	- **开发人员**（1‑3 人）：负责实现生成的代码骨架，并反馈元数据中的错误或不完整之处。
	- **测试人员**（1 人）：负责 STD/STR 中的元数据填写和维护。
	- **代码审查员**（全员）：检查 PR 中是否包含对应 YAML 块的更新。
- **冲突解决**：若两人同时修改同一文档的 YAML 块，Git 合并冲突时，优先保留更完整的版本，然后人工调整差异。建议团队约定同一时间仅一人负责某类文档的元数据填写，或采用分行顺序固定策略减少冲突。

### 1.5.6 人类内容保护机制

当使用 `generate-gb-docs --enhanced` 全量重写国标文档时，文档头部的 `@ai-rewrite` 指令会指导 AI 保留人类撰写的自然语言描述。具体行为：

1. AI 读取 Front Matter 中的 `@ai-rewrite` 指令
2. 识别 `@ai-human-sections` 指定的章节模式
3. 将这些章节的自然语言描述**原样保留**
4. 只更新 YAML 块，或在章节末尾按 `@ai-merge` 策略追加新的结构化内容
5. 新增的章节（原文档不存在）则完整生成自然语言描述和 YAML 块

## 1.7 常见错误与修正

| 错误现象 | 可能原因 | 解决方法 |
|----------|----------|----------|
| YAML 解析失败，提示 "expected <block end>" | 缩进不一致（混用空格和 Tab）| 统一使用 2 个空格缩进，禁用 Tab |
| 字段值被截断 | 字符串中冒号未加引号 | 使用双引号包裹含有冒号的字符串 |
| 多行字符串显示为一行 | 未正确使用 `|` 或 `>` | 使用 `|` 保留换行，推荐使用 `|` |
| 列表中缺少必填字段 | 手动填写遗漏 | 对照规范检查必填字段，补齐缺失项 |
| YAML 块位置错误 | 放在了章节开头而非末尾 | 将 YAML 块移动到章节末尾，且与正文之间空一行 |
| 文档中 YAML 块未被 Skill 识别 | 缺少 `---` 分隔符或标记不规范 | 在每个 YAML 块开头加 `---`（可选但推荐）|
| Git 合并冲突频繁 | 多人同时编辑同一文档的 YAML 块 | 约定专人负责某类文档 |
| Front Matter 中 `@` 键解析失败 | 键名未用引号包裹 | 使用单引号包裹：`'@ai-rewrite'` |
| 全量重写时人类内容丢失 | 未设置 `@ai-rewrite: preserve` | 在 Front Matter 中增加保护指令 |

## 1.8 版本演进机制

- **元数据版本**：本规范版本号使用语义化版本，格式为 `主版本.次版本`（如 `2.0`、`2.1`）。
- **兼容性**：
  - 新增可选字段：向前兼容，旧版本文档可正常解析。
  - 新增必选字段：需要升级主版本，旧工具无法解析时应给出明确警告。
  - 删除字段或修改语义：必须变更主版本，并提供迁移指南。
- **升级策略**：当规范更新时，团队应评估已有文档是否需要迁移。可编写脚本将旧格式 YAML 块批量转换为新格式。建议在 CI 中增加规范版本检查步骤。

## 1.9 附录：针对 2‑5 人团队的补充优化建议

尽管上述规范已完整，但对于小团队，仍有以下可进一步优化的空间：

### 1.9.1 A. 精简字段

- **建议**：对必填字段再审视，例如 `接口` 中的 `协议` 字段在单体应用或内部函数中通常不需要，可设为可选。
- **理由**：小团队项目复杂度较低，过度详细的字段会增加填写负担。可在团队内约定 " 精简模式 "，只填写核心必填字段。

### 1.9.2 B. 模板化

- **建议**：为每种文档提供 **最小模板**，内置元数据的骨架（包含空 YAML 块），团队只需填充关键信息即可。
- **示例**：在项目仓库的 `docs/templates/` 目录下存放 IDD、SDD、DBDD 等国标文档模板，新项目直接复制使用。

### 1.9.3 C. 自动填充工具

- **建议**：开发一个简单的命令行工具（Node.js 脚本），从 `architector` 导出 JSON，再自动注入到指定 Markdown 文档的相应位置。
- **实现**：脚本读取 architector 数据，匹配文档中的章节标题，将生成的 YAML 块插入或替换到对应位置。

### 1.9.4 D. 轻量级 CI 检查

- **建议**：在 CI（如 GitHub Actions）中添加步骤，检查所有国标文档中的 YAML 块是否符合本规范。使用 `yamllint` + 自定义规则。
- **效果**：确保每次代码合并时，元数据质量得到保障，避免后期还原失败。

### 1.9.5 E. 培训与文档

- **建议**：团队成员集体学习本规范，并在项目 Wiki 中提供 **常见场景的元数据填写示例**。
- **理由**：小团队角色重叠，每人可能都需要填写元数据，统一理解可避免格式错误和不一致。
